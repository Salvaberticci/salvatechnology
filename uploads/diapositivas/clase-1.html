> PROCESAMIENTO DE INFORMACIÓN

1. Dato ➔ Información ➔ Sistema

Un software no opera con "magia": procesa datos desestructurados para convertirlos en decisiones automatizadas.

[ 1 ] EL DATO

Un elemento crudo, aislado y sin contexto ni significado propio.

"30"
[ 2 ] LA INFORMACIÓN

Ese dato enmarcado en un contexto que le otorga un sentido útil.

"30 personas en un aula"
[ 3 ] EL SISTEMA

El flujo automatizado que procesa, valida y reacciona a esa información.

Si "30 personas" > Capacidad (25) ➔ Bloquear cupos & Notificar
💡 Definición Central: El **Software** es un conjunto de instrucciones lógicas organizadas en un **Sistema** para convertir **Datos** crudos en **Información** valiosa y ejecutar decisiones automatizadas sin fallos humanos.
> POR QUÉ EXISTE LA INGENIERÍA DE SOFTWARE

2. "Picar Código" vs. Ingeniería de Software

"Picar Código" (Programar sin Plan)

  • ✗ Escribir código improvisado directamente sin arquitectura.
  • ✗ Sin pruebas ni seguridad: colapsa al recibir 100 usuarios reales.
  • ✗ Mantenimiento imposible: arreglar un bug genera 3 bugs nuevos.

Ingeniería de Software

  • ⚡ **Diseñar, construir y mantener** sistemas previsibles.
  • ⚡ Sistemas **Escalables** (aguantan miles de usuarios), **Seguros** y **Eficientes**.
  • ⚡ Metodología rigurosa impulsada por Inteligencia Artificial (ADD).

> BLOQUE 2: ANATOMÍA DE UN SOFTWARE

El Modelo Cliente - Servidor (La Analogía del Restaurante)

EL CLIENTE (Frontend)
Las Mesas, el Menú/Carta y el Mesero

Es la interfaz visible. El usuario se sienta, consulta la carta y realiza su pedido (petición). Es todo lo que el usuario ve, toca e interactúa.

EL SERVIDOR (Backend)
La Cocina y los Chefs

Fuera de la vista del público. Recibe la comanda, valida la receta, aplica las reglas higiénicas/de negocio y cocina la respuesta para el cliente.

LA BASE DE DATOS
La Despensa y la Nevera

El almacén donde están organizados todos los ingredientes (registros). La cocina acude aquí para tomar lo necesario o guardar nuevos suministros.

Protocolo de Comunicación: El Mesero (HTTP Request) lleva la orden a la Cocina y regresa a la Mesa con el plato servido (HTTP Response / JSON).
> BLOQUE 2: EL CLIENTE

Profundizando en el Frontend (La Interfaz)

No es solo "diseño bonito"

El Frontend es la capa de **experiencia e interacción de usuario (UI/UX)**. Es la aplicación ejecutándose localmente en la pantalla del cliente (Navegador, Celular o Escritorio).

Tecnologías Frontend: HTML5 (Estructura), CSS3/Tailwind (Estilos visuales), JavaScript (Lógica de pantalla Web), Python (Desktop) y Flutter (Mobile).

Captura de Eventos

¿Cómo se comunica el ser humano con la máquina? El Frontend escucha continuamente los **eventos del usuario**:

  • 🖱️ **Clics / Taps:** Presionar un botón de "Comprar".
  • ⌨️ **Texto introducido:** Teclear correo y contraseña en formularios.
  • 📱 **Gestos:** Swipe táctil, pellizcar zoom o agitar el teléfono.
⚠️ **Regla de Oro de Seguridad:** Nunca te fíes del Frontend. Todo código en el Frontend puede ser manipulado por un usuario malintencionado en su propio dispositivo.
> BLOQUE 2: EL SERVIDOR

Profundizando en el Backend (Lógica de Negocio)

¿Por qué no podemos poner todo el programa en el Frontend? Por dos pilares innegociables: **Seguridad** y **Capacidad de Procesamiento**.

CASO DE ESTUDIO: VERIFICACIÓN DE SALDO BANCARIO REGLA CRÍTICA
❌ SI ESTUVIERA EN EL FRONTEND (INSEGURO):

Un usuario abre las herramientas de desarrollador (F12) en Chrome, cambia el saldo visual de $5 a $10,000 y presiona "Aprobar Compra". ¡El cliente estafaría al sistema!

✅ PROCESADO EN EL BACKEND (SEGURO):

El cliente solo solicita *"Quiero comprar un producto de $100"*. El Servidor revisa el saldo real oculto en la Base de Datos. Si `Saldo < 100`, **rechaza la transacción de inmediato**. El usuario jamás puede alterar esta regla.

**Lógica de Negocio:** Algoritmos de cobro, encriptación de claves, cálculo de impuestos, envíos de emails y autenticación de identidad.
> BLOQUE 2: PERSISTENCIA

La Base de Datos: RAM vs. Almacenamiento Permanente

¿Qué significa **Persistencia**? Es la capacidad de conservar los datos intactos para que no se borren cuando la computadora, la app o el celular se apagan o se reinician.

⚡ MEMORIA RAM (Volátil / Temporal)
  • • Ultra rápida, pero se **borra por completo** al cortar la energía.
  • • Almacena variables temporales mientras la app está abierta (ej: la pestaña activa del navegador).
  • • Si el celular se apaga, todo lo que estaba solo en RAM desaparece.
💾 BASE DE DATOS (Persistente / Permanente)
  • • Escribe la información en almacenamiento físico (SSD/Disco Duro/Cloud).
  • • Guarda usuarios, claves encriptadas, historial de compras y configuraciones.
  • • **Modelos:** Relacionales (SQL: PostgreSQL, MySQL) y No Relacionales (NoSQL: MongoDB).
Resumen de Arquitectura: Frontend muestra la UI ➔ Backend evalúa las Reglas ➔ Base de Datos guarda la Persistencia.
> BLOQUE 3: ANATOMÍA DE PLATAFORMAS

Plataforma A: Desarrollo Web 🌐

⚙️ FUNCIONAMIENTO & ARQUITECTURA

Vive en un servidor remoto y se ejecuta dentro de un navegador web (Chrome, Safari, Edge, Firefox).

  • 1. El usuario escribe un dominio URL en el navegador.
  • 2. Descarga archivos remotos: **HTML, CSS y JavaScript**.
  • 3. Se comunica con el Backend usando el protocolo **HTTP / HTTPS**.
⚖️ BALANCE TÉCNICO
🟢 Ventajas:

Acceso universal desde cualquier dispositivo con internet. **0 Instalación requerida** por el cliente.

🔴 Limitaciones:

Dependencia total de conexión a internet. Acceso muy restringido al hardware local por políticas de seguridad del navegador.

Casos de Uso Ideales: E-commerce, plataformas de educación, portales bancarios y SaaS globales.
> BLOQUE 3: ANATOMÍA DE PLATAFORMAS

Plataforma B: Desarrollo Desktop 💻

⚙️ FUNCIONAMIENTO & ARQUITECTURA

Se instala e integra directamente con el Sistema Operativo (Windows, macOS, Linux).

  • • Aprovecha la potencia bruta de la **CPU, GPU y Memoria RAM** del PC.
  • • Puede funcionar 100% **Offline** almacenando datos locales en SQLite o archivos JSON.
⚖️ BALANCE TÉCNICO
🟢 Ventajas:

Acceso total al hardware: Lectores de código USB, impresoras fiscales térmicas, escáneres y discos duros ultrarrápidos.

🔴 Limitaciones:

Requiere instalación manual en cada equipo y despliegue de actualizaciones máquina por máquina.

Casos de Uso Ideales: Puntos de Venta (POS) en cajas registradoras, editores de video/3D, sistemas médicos industriales.
> BLOQUE 3: ANATOMÍA DE PLATAFORMAS

Plataforma C: Desarrollo Móvil 📱

📱 RECURSOS & CICLO DE VIDA

Instalada en smartphones (Android / iOS). Diseñada para **recursos limitados (batería y RAM)**.

• **Primer Plano:** Usuario interactuando directamente.
• **Segundo Plano:** Minimizada ahorrando energía.
• **Destruida:** S.O. la liquida para liberar memoria.
⚖️ BALANCE TÉCNICO
🟢 Ventajas:

Acceso nativo a sensores: **GPS, Cámara, Bluetooth, Acelerómetro y Notificaciones Push**.

🔴 Limitaciones:

Restricciones estrictas y comisiones de las tiendas oficializadas (**Google Play** y **Apple App Store**).

Casos de Uso Ideales: Apps de Delivery, redes sociales, transporte GPS, billeteras digitales móviles.
> BLOQUE 4: DESMONTANDO UN SOFTWARE REAL

Caso Práctico: Sistema de Inventario & Ventas

Las tres plataformas no compiten entre sí: **se complementan** dentro del mismo ecosistema empresarial.

1. DESKTOP (El Cajero)

El empleado en la tienda usa la app de escritorio para escanear productos a toda velocidad con un **lector USB** e imprimir el ticket fiscal sin demoras.

2. WEB (El Dueño)

El dueño abre Chrome en su laptop personal desde cualquier lugar del mundo para ver el **Dashboard de ventas en tiempo real** e inventario general.

3. MOBILE (El Repartidor)

El chofer abre la app móvil para ver la ruta óptima en **GPS** hasta la casa del cliente y solicitar su **firma digital** al entregar el pedido.

🔥 PUNTO CLAVE DE ARQUITECTURA: Las 3 aplicaciones totalmente distintas conversan con la **misma Capa Backend** y consultan la **misma Base de Datos Cloud**.

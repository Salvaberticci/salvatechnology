CAPÍTULO 1 // LA TRIADA DEL SOFTWARE

Responsabilidades Claras de Cada Capa

Bienvenido de nuevo a SalvaTechnology Academy. Hoy damos un salto técnico fundamental: la delimitación estricta de responsabilidades entre Frontend, Backend y Base de Datos. Un error común en programadores principiantes es mezclar lógica de negocio en la interfaz, o hacer que la base de datos procese validaciones complejas. Para construir sistemas escalables debemos establecer una frontera técnica infranqueable.

🖥️ EL FRONTEND — PRESENTACIÓN E INTERACCIÓN

Única responsabilidad: la interfaz humana y el estado visual. Renderiza la pantalla, captura el teclado/clics/gestos, valida estéticamente y muestra cargando/error/éxito. Vive en el dispositivo del usuario.

= CLIENTE · DISPOSITIVO DEL USUARIO

🔒 Toca para ver explicación

⚙️ EL BACKEND — LÓGICA, NEGOCIO Y ORQUESTACIÓN

Autoridad central y motor del sistema. Valida autenticidad y permisos, aplica reglas matemáticas/comerciales, procesa algoritmos pesados y orquesta lecturas/escrituras hacia la persistencia.

= SERVIDOR REMOTO BAJO NUESTRO CONTROL

🔒 Toca para ver explicación

🗄️ LA BASE DE DATOS — PERSISTENCIA Y ESTRUCTURA

Conservación duradera, organizada y segura de la información. Garantiza que los datos sobrevivan al tiempo, mantiene integridad referencial y consulta rápido millones de filas o documentos.

= ALMACENAMIENTO PERSISTENTE

🔒 Toca para ver explicación

La Triada en una Frase

"El Frontend pide y muestra; el Backend decide y procesa; la Base de Datos almacena y recuerda"

Cada capa tiene una sola razón de cambio. Si un cambio de reglas de negocio obliga a tocar el HTML, o un cambio de validación obliga a reescribir tablas, tu frontera técnica está rota.

CAPÍTULO 2 // EL MAPA DE UBICACIÓN DEL DATO

¿Dónde Vive Cada Dato?

La pregunta técnica más importante del diseño: ¿dónde reside cada dato en cada instante del tiempo? Un dato no flota en el aire; ocupa un espacio físico de memoria según su ciclo de vida y su propósito. Clasifiquemos las 4 ubicaciones fundamentales.

📍 UBICACIÓN 1 · RAM DEL CLIENTE

Datos efímeros de interfaz: texto sin enviar, scroll, modal visible, filtros visuales. Si cierras la pestaña o recargas, desaparecen.

🔒 Toca para ver explicación

📍 UBICACIÓN 2 · PAQUETE DE RED

El dato mientras viaja por cables o antenas: empaquetado en JSON, con credenciales, tokens JWT en headers y datos del formulario.

🔒 Toca para ver explicación

📍 UBICACIÓN 3 · MEMORIA DEL SERVIDOR

Datos de proceso en ejecución: variables calculadas en transacciones, claves de desencriptación y sesiones activas en caché de alta velocidad (Redis).

🔒 Toca para ver explicación

📍 UBICACIÓN 4 · DISCO DE LA BD

La Single Source of Truth: saldos, historial de compras, hashes de contraseñas, comentarios y fotos. Lo único que debe perdurar.

🔒 Toca para ver explicación

El viaje del dato:
RAM DEL CLIENTE → PAQUETE DE RED (JSON) → MEMORIA DEL SERVIDOR → DISCO DE LA BD

CAPÍTULO 3 // LA AUTOPISTA DE COMUNICACIÓN

¿Cómo se Hablan las Capas?

La comunicación sigue un protocolo estricto dividido en dos grandes puentes: Frontend ↔ Backend vía HTTP/REST, y Backend ↔ Base de Datos vía drivers, ORM y SQL/NoSQL.

Puente 1 · Frontend ↔ Backend — HTTP / REST API

El Frontend NO tiene acceso directo a la Base de Datos. Emite peticiones HTTP con verbos estándar:

GET → leer datos
POST → crear registro
PUT/PATCH → actualizar
DELETE → eliminar
Respuesta con código de estado: 200 OK (éxito), 401 Unauthorized (no autenticado), 404 Not Found (no existe) — y cuerpo JSON.
Puente 2 · Backend ↔ Base de Datos — Drivers, ORM y SQL

Tras validar reglas de negocio, el Backend se conecta con un Driver u ORM y habla el lenguaje nativo de la BD:

SQL (MySQL, PostgreSQL) — consultas relacionales estructuradas
NoSQL (MongoDB) — consultas por documentos

La BD procesa la consulta en su motor, lee/escribe en el disco y devuelve la fila o documento. El Backend lo transforma en JSON limpio y lo envía por la red al Frontend para pintarlo.

El Viaje del Dato: Publicar un Comentario

Rastreemos un flujo real de principio a fin: publicar "¡Excelente clase!" en una plataforma web. Un viaje de 5 pasos a través de las tres capas.

PASO 1 · FRONTEND CAPTURA

Escribes el texto (vive en la RAM del Frontend) y al pulsar "Publicar" se emite POST /api/comentarios con el texto y el ID de la publicación en JSON.

🔒 Toca para ver explicación

PASO 2 · BACKEND: ADUANA DE SEGURIDAD

Extrae el JWT del header para identificar al usuario, filtra spam/palabras prohibidas y verifica que el usuario no esté bloqueado.

🔒 Toca para ver explicación

PASO 3 · BASE DE DATOS INSERTA

INSERT INTO comentarios (usuario_id, post_id, contenido) VALUES (45, 102, '¡Excelente clase!') — escribe en disco, genera el ID y confirma.

🔒 Toca para ver explicación

PASO 4 · RESPUESTA AL FRONTEND

El Backend responde 201 Created con el JSON del nuevo comentario creado.

🔒 Toca para ver explicación

PASO 5 · RENDERIZADO EN EL FRONTEND

El Frontend recibe el JSON, destruye el texto del cajón en su RAM y renderiza la nueva burbuja de comentario en pantalla.

🔒 Toca para ver explicación

-- Paso 3: la Base de Datos persiste la verdad

VALUES (45, 102, '¡Excelente clase!');
-- -> ID único generado, dato en disco, COMMIT confirmado al Backend

CAPÍTULO FINAL // SÍNTESIS MAGISTRAL

Síntesis & Actividad 1.3

Síntesis ejecutiva: el Frontend presenta la interfaz, maneja la UX y captura eventos; el Backend procesa la lógica de negocio, blinda la seguridad y orquesta la comunicación; la Base de Datos mantiene la persistencia permanente e íntegra. Los datos migran desde la RAM del cliente, se empaquetan en JSON vía HTTP, se procesan en el servidor y se aseguran en el disco.

Puntos Clave

  • → Triada: Frontend pide y muestra; Backend decide y procesa; BD almacena y recuerda.
  • → Mapa del dato: RAM del cliente → JSON en red → memoria del servidor → disco de la BD.
  • → Comunicación: HTTP/REST (GET, POST, PUT/PATCH, DELETE) + SQL/NoSQL.
  • → Flujo real: POST /api/comentarios → aduana JWT → INSERT SQL → 201 Created → renderizado.

CAPÍTULO 1 // FUNDAMENTOS

Dato → Información → Sistema

Bienvenido, recluta. Antes de escribir una sola línea de código, debes entender algo fundamental: un software no opera con "magia". Todo sistema informático procesa datos desestructurados para convertirlos en decisiones automatizadas. Vamos a ver cómo ocurre esa transformación.

[ 1 ] EL DATO

Un elemento crudo, aislado y sin contexto ni significado propio. Por sí solo no dice nada.

"30"

🔒 Toca para ver explicación

[ 2 ] LA INFORMACIÓN

Ese dato enmarcado en un contexto que le otorga un sentido útil para la toma de decisiones.

"30 personas en un aula"

🔒 Toca para ver explicación

[ 3 ] EL SISTEMA

El flujo automatizado que procesa, valida y reacciona a esa información en tiempo real.

Si "30 personas" > Capacidad (25) ➔ Bloquear cupos & Notificar

🔒 Toca para ver explicación

Definición Central: El Software es un conjunto de instrucciones lógicas organizadas en un Sistema para convertir Datos crudos en Información valiosa y ejecutar decisiones automatizadas sin fallos humanos.
data-pipeline.php
// Ejemplo conceptual: Dato → Información → Decisión
$datoCrudo = "30"; // Solo un número, sin contexto
$contexto = "personas en el aula";
$informacion = $datoCrudo . " " . $contexto; // "30 personas en el aula"

// El sistema evalúa y decide automáticamente:
if ($informacion > CAPACIDAD_MAXIMA) {
  bloquearCupos();
  notificarUsuario("Cupos agotados");
} else {
  confirmarInscripcion();
}

Analogía del Mundo Real

Imagina que ves el número "30" escrito en una pizarra. Eso es un dato. No sabes si son grados, personas, días o dinero. Ahora alguien te dice: "son 30 estudiantes esperando en la sala de conferencias". Eso es información. Tiene contexto.

Ahora, tú como sistema dices: "la sala solo tiene 25 sillas, así que rechazo a 5 personas y envío una notificación". Eso es el sistema actuando. Así funciona TODO software: desde una red social hasta un cajero automático.

CAPÍTULO 2 // INGENIERÍA VS CÓDIGO

"Picar Código" vs. Ingeniería de Software

Hay una diferencia abismal entre programar por programar (lo que llamamos "picar código") y hacer Ingeniería de Software. Uno es como construir una caseta de madera sin planos. El otro es como diseñar un rascacielos que resistirá terremotos. Vamos a ver las diferencias.

"Picar Código"

  • ✗ Sin planificación: Se escribe código improvisado directamente, resolviendo sobre la marcha.
  • ✗ Sin estructura: No hay separación de responsabilidades, todo está mezclado.
  • ✗ Sin pruebas: El código no se testea. Al recibir 100 usuarios reales, colapsa.
  • ✗ Deuda técnica infinita: Arreglar un bug genera 3 bugs nuevos. Mantenimiento imposible.
  • ✗ Solo tú lo entiendes: Si te atropella un bus, el proyecto muere contigo.

Ingeniería de Software

  • ⚡ Planificación rigurosa: Se diseña antes de construir. Arquitectura primero.
  • ⚡ Separación de capas: Frontend, Backend y BD bien diferenciados y modulares.
  • ⚡ Testing automatizado: Pruebas unitarias, de integración y de carga en cada fase.
  • ⚡ Escalabilidad: El sistema soporta desde 10 hasta 1 millón de usuarios sin colapsar.
  • ⚡ Trabajo en equipo: Cualquier ingeniero puede entender y modificar el código.
> EL CICLO DE VIDA DEL SOFTWARE (SDLC):

Todo software profesional sigue estas 6 etapas. Saltarse una sola es condenarse al fracaso.

1. Requerimientos Entender el problema real del cliente
2. Diseño Arquitectura del sistema, DB, UI
3. Desarrollo Codificación con metodología ADD
4. Pruebas QA Validar seguridad, errores, rendimiento
5. Despliegue Salida a producción (servidores)
6. Mantenimiento Soporte, bugs, nuevas features

Analogía: La Casa vs. El Rascacielos

🏚️ Picar Código = Caseta de Playa

Coges madera y clavos y empiezas a construir sin planos. Tal vez quede bonita al principio, pero cuando llegue una tormenta (crecimiento de usuarios), se derrumbará. No tiene cimientos, no tiene estructura. Arreglar una pared puede tirar el techo.

🏢 Ingeniería = Rascacielos

Arquitectos, ingenieros civiles, maquetas digitales, estudios de suelo, planos estructurales. Cada viga tiene un propósito. Los ascensores (APIs) están diseñados para mover miles de personas. Cuando hay un terremoto (pico de tráfico), el edificio no colapsa: se mece y resiste.

CAPÍTULO 3 // ARQUITECTURA

Anatomía de 3 Capas

Esta es la clave que todo ingeniero debe dominar: toda aplicación moderna, sin importar si es Web, Desktop o Mobile, comparte exactamente la misma anatomía de 3 capas. Aprende esto y podrás entender cualquier sistema que veas en tu carrera.

FRONTEND

Es la cara visible del sistema. Todo lo que el usuario ve y toca.

  • Web: HTML + CSS + JavaScript (PHP/Laravel)
  • Desktop: Python
  • Mobile: Flutter
Se ejecuta en el dispositivo del usuario
BACKEND

Es el cerebro. Procesa peticiones y ejecuta la lógica de negocio.

  • API REST: PHP (Laravel)
  • Lógica: Autenticación, Pagos, Validaciones
  • Eventos: Colas de mensajes, WebSockets
Se ejecuta en el servidor (nube)
PERSISTENCIA

Es la memoria permanente. Donde vive la información.

  • SQL: MySQL, PostgreSQL, SQL Server
  • NoSQL: MongoDB, Redis, Firebase
  • Archivos: JSON, CSV, PDFs, Imágenes
Se ejecuta en el servidor de BD
El Flujo Completo:
👤 Usuario → 🖥️ Frontend → ⚙️ Backend → 🗄️ Base de Datos

El usuario hace clic → Frontend envía petición → Backend procesa → DB guarda/consulta → Respuesta vuelve → Frontend actualiza la pantalla. Todo en milisegundos.

Ejemplo Real: Un Restaurante

🖥️ Frontend = Mesero

Toma tu orden, te muestra el menú, te trae la cuenta. Es lo único que tú ves como cliente.

⚙️ Backend = Cocina

El chef recibe la orden, aplica las recetas (reglas de negocio), verifica ingredientes y cocina.

🗄️ DB = Despensa/Refri

Donde se guardan los ingredientes. Si no hay tomates en la despensa, la cocina no puede hacer salsa.

CAPÍTULO 4 // PATRONES

MVP, MVC y Patrones Arquitectónicos

Los patrones arquitectónicos son plantillas probadas para organizar tu código. El más famoso de todos es MVC (Model-View-Controller). Si entiendes MVC, entiendes el 80% de las aplicaciones del mundo. Vamos a verlo a fondo.

MVP (Model-View-Presenter)

Antepasado de MVC. La Vista es pasiva y el Presenter orquesta todo.

  • 🎯 Model: Representa los datos y reglas de negocio.
  • 🎯 View: Interfaz pasiva, solo muestra lo que el Presenter le dice.
  • 🎯 Presenter: Orquesta toda la comunicación. Fácil de testear.
// MVP: Presenter controla todo
class UserPresenter {
  constructor(view, model) {
    this.view = view;
    this.model = model;
  }
  onUserClick(id) {
    const user = this.model.getUser(id);
    this.view.showUser(user); // View solo ejecuta
  }
}

MVC (Model-View-Controller)

El rey de los patrones. Usado en Laravel, Rails, Spring, Django y más.

  • 🎯 Model: Datos + Estado + Lógica de negocio.
  • 🎯 View: Renderiza la interfaz (se suscribe a cambios del Model).
  • 🎯 Controller: Recibe input del usuario y coordina Model y View.
// MVC clásico en PHP (similar a Laravel)
class UserController {
  public function show(int $id): Response {
    $user = User::find($id); // Model
    return view('profile', ['user' => $user]); // View
  }
}

¿Por qué son importantes los patrones?

🧪 Testeable

Al separar responsabilidades, puedes probar cada pieza por separado. El controlador se testea sin la vista.

🔄 Reutilizable

Puedes cambiar la vista (de web a móvil) sin tocar el modelo ni el controlador. El negocio sigue intacto.

👥 Colaborativo

Un equipo trabaja en la vista, otro en el controlador, otro en el modelo. Todos en paralelo sin pisarse.

💡 Dato Clave: Esta misma plataforma educativa que estás usando ahora mismo (SalvaTechnology Academy) está construida con una arquitectura MVC. Cada lección, cada actividad, cada usuario — todo sigue el patrón Model-View-Controller. No es teoría abstracta: es código real funcionando aquí y ahora.

CAPÍTULO 5 // METODOLOGÍA ADD

Arquitectura Dirigida por IA

ADD son las siglas de Arquitectura Dirigida por Inteligencia Artificial (AI-Driven Design). Es la metodología de vanguardia que usamos en SalvaTechnology: usar asistentes de IA como motores de arquitectura y generación de código. No es "reemplazar al programador" — es potenciarlo.

> LOS 3 PILARES DE ADD:
1

Definir con Precisión

Describe el problema al asistente IA con claridad quirúrgica. Entre más específico seas, mejor será la arquitectura generada.

2

Diseñar con IA

La IA propone la arquitectura: estructura de carpetas, componentes, flujo de datos, modelo de base de datos y APIs.

3

Implementar y Pivotear

Itera con la IA para refactorizar, escalar, optimizar y depurar el código. Un diálogo constante de mejora.

Ejemplo de Prompt ADD (lo que le dices a la IA):
/* Prompt para OpenCode (Vibe Coding) */
"Actúa como arquitecto de software senior especializado en PHP y MySQL. Diseña la arquitectura completa de un sistema de e-learning con las siguientes características:

- Dos roles de usuario: Estudiante y Profesor
- Sistema de suscripciones con planes: 1 mes ($40), 3 meses ($110), 6 meses ($190)
- Gestión de actividades y entregas con calificaciones
- Chat en tiempo real entre estudiantes y profesores

Proporciona: estructura de carpetas, esquema de base de datos (5-7 tablas), y el flujo de API REST requerido."

¿Por qué ADD cambia las reglas del juego?

🚀

Velocidad 10x: Lo que antes tomaba 1 semana en diseñar, ahora toma 1 hora con la IA.

🧠

Experiencia Colectiva: La IA ha sido entrenada con millones de proyectos. Aprovecha el conocimiento de la industria global.

🔄

Iteración Infinita: Puedes pedir cambios, refactors y mejoras al instante. Sin esperar reuniones.

🎓

Aprendizaje Acelerado: Cada interacción con la IA te enseña patrones, buenas prácticas y nuevas tecnologías.

CAPÍTULO 6 // MULTIPLATAFORMA

Web vs Desktop vs Mobile

Una misma arquitectura de 3 capas se aplica a cualquier plataforma. La diferencia está en el Frontend: cambia la tecnología, pero el Backend y la Base de Datos pueden ser exactamente los mismos. Así es como empresas como Netflix, Spotify o Uber tienen apps en web, iOS, Android y TV.

🌐 WEB

Accesible desde cualquier navegador. No requiere instalación.

  • Frontend: HTML + CSS + JS (Laravel/Blade)
  • Backend: PHP (Laravel)
  • Distribución: URL pública

🖥️ DESKTOP

Aplicaciones instaladas en Windows, Mac o Linux.

  • Frontend: Python
  • Backend: El mismo servidor web existente
  • Distribución: Instalador .exe / .dmg

📱 MOBILE

Apps nativas en iOS y Android. Máximo alcance.

  • Frontend: Flutter
  • Backend: El mismo servidor web existente
  • Distribución: App Store / Play Store

El Backend es el Centro del Universo

Aquí está el secreto que cambia tu perspectiva: cuando construyes una API REST bien diseñada, un solo backend puede alimentar simultáneamente una página web, una app de escritorio, una app móvil iOS, una app Android, un smart TV, e incluso un asistente de voz como Alexa. Todos consumen los mismos endpoints, la misma lógica de negocio, la misma base de datos.

Esto se llama omnicanalidad — y es el estándar de la industria moderna.

api/users.php (REST Endpoint)
// Este mismo endpoint sirve para Web, Desktop y Mobile
header('Content-Type: application/json');

$users = User::all(); // Consulta a la BD
echo json_encode([
  'status' => 'success',
  'data' => $users
]);

// ✅ Web: fetch('/api/users.php') → renderiza HTML (PHP/Laravel)
// ✅ Desktop (Python): requests.get('api/users.php') → renderiza la ventana
// ✅ Mobile (Flutter): http.get('api/users.php') → renderiza las vistas

CAPÍTULO 7 // CASOS REALES

Arquitectura en Empresas Reales

Todo lo que has aprendido no es teoría académica. Cada gran empresa tecnológica del mundo usa exactamente estos mismos principios. Vamos a ver cómo aplican la arquitectura de 3 capas algunos gigantes de la industria.

Netflix

Sirve 200M+ usuarios en 190 países.

  • Frontend: React (Web) + Apps nativas (iOS/Android/TV)
  • Backend: Microservicios, API Gateway
  • DB: Cassandra (NoSQL) + PostgreSQL + S3 para videos

Spotify

Transmite música a 500M+ usuarios.

  • Frontend: React (Web) + Apps nativas (Desktop/Mobile)
  • Backend: Python + Java, más de 1000 microservicios
  • DB: PostgreSQL + Cassandra + BigTable

Meta (Facebook)

Conecta a 3B+ personas globalmente.

  • Frontend: React (Web) + Apps nativas (Mobile)
  • Backend: PHP (Hack) + Python + Go
  • DB: MySQL (sharded) + Redis + TAO (graph)

Amazon

El comercio electrónico más grande del mundo.

  • Frontend: React (Web) + Apps nativas
  • Backend: Java (millones de microservicios)
  • DB: DynamoDB (NoSQL) + Aurora (SQL) + S3
💡 Reflexión: ¿Notas el patrón? TODAS tienen Frontend, Backend y Base de Datos. Lo que cambia son las tecnologías específicas, pero la arquitectura conceptual es idéntica. Aprende la arquitectura una vez, aplícala en cualquier tecnología.
